Referencia de API y protocolos

Peak Auth expone interfaces estándar para descubrimiento OIDC, flujos de autorización OAuth 2.0 con PKCE, M2M Client Credentials, y una API REST directa con rotación criptográfica de sesiones.

Discovery OIDC & JWKS

Endpoints públicos con cabeceras CORS habilitadas para que SDKs, librerías estándar OIDC y clientes puedan resolver la configuración y las claves públicas de validación de forma autónoma.

GET /.well-known/jwks.json

Retorna el conjunto de claves públicas en formato estándar JWK (RFC 7517), incluyendo la clave activa actual y claves previas válidas durante períodos de rotación (kid).

JSON 
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "peak-auth-key-1",
      "n": "<MODULO_RSA_BASE64URL>",
      "e": "AQAB"
    }
  ]
}
GET /.well-known/openid-configuration

Metadatos de descubrimiento OpenID Connect con las URLs canónicas del servidor de autenticación (authorization_endpoint, token_endpoint, jwks_uri, etc.).

OAuth 2.0 con PKCE (Flujo de autorización SSO)

Recomendado para aplicaciones web, SPAs (Angular, React, Vue) y móviles. Permite autenticación centralizada con sesión compartida.

GET /oauth/authorize
HTTP GET 
GET /oauth/authorize?response_type=code
  &client_id=mi-app-id
  &redirect_uri=https%3A%2F%2Fmi-app.com%2Fcallback
  &code_challenge=<CODE_CHALLENGE>
  &code_challenge_method=S256
  &state=<STATE>
POST /oauth/token

Intercambia el código de autorización por los tokens definitivos (Access Token + Refresh Token).

JSON 
{
  "grant_type": "authorization_code",
  "client_id": "mi-app-id",
  "client_secret": "<CLIENT_SECRET>",
  "code": "<AUTHORIZATION_CODE>",
  "redirect_uri": "https://mi-app.com/callback",
  "code_verifier": "<CODE_VERIFIER>"
}

POST /oauth/token (Client Credentials - RFC 6749)

Autenticación Machine-to-Machine (M2M) para microservicios y workers. Admite credenciales en cabecera HTTP Basic Auth (Authorization: Basic base64(client_id:client_secret)) o en el cuerpo de la petición.

JSON Request 
{
  "grant_type": "client_credentials",
  "client_id": "mi-microservicio-id",
  "client_secret": "<CLIENT_SECRET>",
  "scope": "service:read service:write"
}

Respuesta

JSON Response 
{
  "access_token": "ey...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "service:read service:write"
}

POST /oauth/introspect (RFC 7662)

Permite a gateways y APIs consultar el estado activo y metadatos de un token en tiempo real:

HTTP Request 
POST /oauth/introspect
Headers: Content-Type: application/x-www-form-urlencoded
Body: token=<ACCESS_TOKEN>

Social Login (Identity Brokering)

Endpoints para iniciar sesión social y delegar la autenticación en proveedores externos:

  • GET /oauth/broker/:provider/auth (Donde :provider puede ser google o github)
  • GET /oauth/broker/:provider/callback (Callback procesado de forma atómica y segura)

POST /api/v1/login (Headless / Móvil)

Para clientes móviles nativos o aplicaciones que requieren autenticación directa sin interfaz web de redirección. Si el usuario tiene MFA activo o la aplicación lo exige mediante políticas, retorna un token temporal mfa_pending.

JSON Request 
{
  "email": "usuario@ejemplo.com",
  "password": "<PASSWORD>",
  "client_id": "mi-app-id",
  "client_secret": "<CLIENT_SECRET>"
}

Desafío MFA

Si se requiere un segundo factor, intercambia el token mfa_pending en:

  • POST /api/v1/login/mfa/totp (código de 6 dígitos)
  • POST /api/v1/login/mfa/recovery (código de recuperación)
  • POST /api/v1/login/mfa/webauthn/register/finish (afirmación FIDO2/Passkey)

POST /api/v1/refresh

Renueva el Access Token utilizando un Refresh Token válido. Implementa rotación criptográfica estricta con hash SHA-256: al consumirse el refresh token actual, es invalidado inmediatamente y se emite uno nuevo.

JSON Request 
{
  "refresh_token": "<REFRESH_TOKEN>",
  "client_id": "mi-app-id"
}

Gestión de sesiones activas y revocación

Endpoints protegidos mediante JWT para auditoría y control de dispositivos conectados:

  • GET /api/v1/user/sessions (Lista sesiones activas y dispositivo actual)
  • DELETE /api/v1/user/sessions/:id (Revoca una sesión específica)
  • POST /api/v1/user/sessions/revoke-others (Revoca todas las demás sesiones excepto la actual)

Health probes & observabilidad

Diseñados para balanceadores de carga, Docker y Kubernetes:

  • GET /health (Liveness probe con tiempo de actividad)
  • GET /ready (Readiness probe con verificación activa de PostgreSQL y claves JWT)

Validación en tu aplicación (SDKs oficiales)

Tu backend NO debe llamar a Peak Auth en cada petición. Los SDKs oficiales consultan el endpoint JWKS, cachean las claves públicas en memoria y validan la firma criptográfica RSA-256, expiración y audiencia de forma 100% local y con latencia cero.

1. TypeScript / Node.js (@brunotarditi/peak-auth)

TypeScript 
import { createPeakAuthClient } from "@brunotarditi/peak-auth";
import { peakAuthExpress } from "@brunotarditi/peak-auth/express";

const client = createPeakAuthClient({
  baseUrl: "https://auth.tu-dominio.com",
  clientId: "mi-app-id",
});

// Middleware Express automático:
app.use("/api", peakAuthExpress({ 
  baseUrl: "https://auth.tu-dominio.com", 
  clientId: "mi-app-id" 
}));

// O verificación manual en cualquier endpoint:
const claims = await client.verifyToken(token);
console.log("Usuario autenticado:", claims.email, claims.roles);

2. Go (github.com/brunotarditi/peak-auth/sdk/go)

Go 
import (
    peakauth "github.com/brunotarditi/peak-auth/sdk/go"
    ginpeak  "github.com/brunotarditi/peak-auth/sdk/go/gin"
)

client, err := peakauth.NewClient(peakauth.Config{
    BaseURL:  "https://auth.tu-dominio.com",
    ClientID: "mi-app-id",
})

// Middleware para Gin Web Framework:
r.GET("/protegido", ginpeak.AuthMiddleware(client), func(c *gin.Context) {
    claims, _ := ginpeak.GetClaims(c)
    c.JSON(200, gin.H{"user": claims.Email, "roles": claims.Roles})
})

3. Kotlin / Android (io.peakauth:peak-auth-kotlin)

Kotlin 
import io.peakauth.PeakAuthClient
import io.peakauth.PeakAuthConfig

val client = PeakAuthClient(
    PeakAuthConfig(
        baseUrl = "https://auth.tu-dominio.com",
        clientId = "mi-app-id"
    )
)

// Verificación offline con corrutinas de Kotlin:
val result = client.verifyToken(accessToken)
result.onSuccess { claims ->
    println("Bienvenido ${claims.email}, roles: ${claims.roles}")
}.onFailure { error ->
    println("Token inválido: ${error.message}")
}
